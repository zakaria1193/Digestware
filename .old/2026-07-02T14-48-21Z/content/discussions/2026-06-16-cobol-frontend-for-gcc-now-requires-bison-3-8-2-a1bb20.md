primer_expert: The GCC COBOL frontend uses Bison to generate parsers. This change
  addresses One Definition Rule (ODR) violations, particularly relevant for Link-Time
  Optimization (LTO) in C++. By wrapping Bison-generated code in a C++ namespace,
  it ensures symbol uniqueness and prevents conflicts. The dependency on Bison 3.8.2
  arises from its improved C++ support for namespace declarations and `std::iostream`
  integration, which older versions lack. This impacts the build environment for GCC/COBOL
  and necessitates an updated Bison version.
primer_general: A compiler like GCC needs a parser to understand the code you write.
  This parser is often generated by a tool like Bison. When different parts of a large
  program (like GCC) are compiled and then linked together, there are rules about
  how many times a particular piece of code (like a function or variable) can be defined.
  These are called One Definition Rule (ODR) violations, and they can cause subtle
  and hard-to-find bugs. This proposal updates the COBOL part of GCC to use the latest
  version of Bison (3.8.2). This new Bison version allows the generated parser code
  to be put into its own 'namespace' (a way of organizing code in C++ to prevent name
  clashes), which helps avoid these ODR violations, especially when the entire program
  is optimized at the very end of the compilation process (Link-Time Optimization,
  or LTO). The change means anyone building GCC with COBOL support will need to ensure
  they have Bison 3.8.2 installed.

James K. Lowden announced an update to the GCC COBOL frontend that now requires Bison 3.8.2. This change addresses ODR violations by wrapping Bison output in a C++ namespace. The upgrade is necessary because older Bison versions lack the required C++ support. The new implementation also uses `std::iostream` for diagnostic messages.
