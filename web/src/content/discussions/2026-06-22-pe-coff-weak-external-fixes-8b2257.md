  a symbol might have a 'weak' definition that can be overridden by a 'strong' definition

primer_general: When a computer program is built, it often combines many separate
  pieces of code, called 'object files,' into a single executable. This process is
  called 'linking,' and it's handled by a special tool called a 'linker.' Sometimes,
  a program might declare a 'weak external symbol' — essentially, a placeholder for
  a function or variable that might exist in another part of the program or in a library.
  If a 'strong' (definitive) version of that symbol is found, the strong one is used.
  Otherwise, the 'weak' one (or a default 'fallback' value) is used. This proposal
  addresses bugs in how the Binutils linker (specifically, its BFD component) handles
  these weak symbols in PE-COFF files, which are the standard executable format for
  Windows. Incorrect handling can lead to programs behaving unexpectedly or crashing,
  so fixing these issues and adding tests ensures that software built with Binutils
  for Windows is stable and correct.

This patch series, now in its second version, addresses two critical bugs in how the BFD linker resolves weak external symbols for PE-COFF binaries. The fixes specifically target scenarios where a strong undefined symbol is encountered before a weak one, and how fallback symbols are prioritized, especially when dealing with null fallbacks. To prevent regressions and ensure correctness, the author has also added a comprehensive suite of new tests covering various weak/strong symbol interaction matrices, crucial for maintaining the stability of Windows binaries generated by Binutils.
